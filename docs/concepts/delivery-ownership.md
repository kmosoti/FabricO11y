# Delivery ownership

An event has a **retryable owner** when the upstream sender still has a copy it can send again. It has a **durable owner** when a receiver commit has completed and the event can be recovered after the receiver crashes. These are protocol responsibilities, separate from Rust's memory ownership of an `Event` value.

The target handoff has this order: receive into volatile memory, commit durably, deliver an acknowledgement, then let the sender forget. Acknowledging earlier lets the sender discard its copy while the receiver may still lose its volatile copy. The [delivery architecture](../architecture/delivery.md) shows the states, and the [TLA+ model](../../formal/delivery/README.md) checks the rule for two events.

In the default [demo](../../src/main.rs), `EventBuffer::try_push` transfers Rust ownership into memory and `take_batch` transfers it back to the caller. Neither call establishes a durable owner. The optional `write` command passes each drained event by reference to the [event log](event-log.md), which returns only after local file sync. It then releases the value. This demonstrates the receiver-side boundary, but there is still no independent sender or delivered ACK. `append(&Event)` does not consume the caller's value on error; the caller remains responsible for it. The demo CLI exits on error and can reconstruct its synthetic source on an ordinary restart with the same settings, but automatic reuse of a path after a storage I/O error is unsafe. See the [storage failure assumptions](../architecture/storage.md#failure-behavior-and-assumptions).
