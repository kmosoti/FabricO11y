# Prospective native early row-release prototype

## Contract and mechanism

This registered supplement to [native frontier protocol](native-frontier-protocol.md) varies one ownership lifetime in the existing bounded Fabric sealer. Baseline and candidate both use local signal run cap **8 MiB**; defaults remain the ordinary 16 MiB run cap with early release disabled. `FABRIC_EARLY_ROW_RELEASE_EXPERIMENT` is accepted only unset (baseline) or exactly `1` (candidate); every other value fails compilation. Shared staging is deferred.

In `Table::flush`, filters are built while source rows exist. Successful conversion produces an owned Arrow RecordBatch; candidate then clears source rows before Parquet encoding. Both policies explicitly drop the RecordBatch after `writer.write` returns and **before `writer.flush`**, preserving the original temporary lifetime. Row count is captured before clearing and published to the internal count only after successful write/flush. Source Vec spare capacity remains allocated. On conversion error, source rows remain; on write error, candidate source rows have been released but durable journal custody remains and the failed build cannot publish a manifest. Existing build cleanup and commit order are unchanged. No formats, compression, row-group boundaries, sorting, spill schedule, filter construction or public oracle change.

The causal candidate comes from the prior phase diagnostic: source raw batches coexist with owned Arrow arrays and Parquet encoder transients at the observed peak. H1 is a ≥10% reduction in requested whole-build peak heap against local8 baseline, while all bytes and semantic gates agree, throughput remains ≥90%, and whole-native CPU/RSS remain ≤110%. H0 is failure of any benefit/guard or semantic mismatch. Conversion can itself remain the dominant peak, making release too late to help. Smaller outputs may expose encoder/drop costs without useful memory reduction. These are meaningful null/adverse outcomes, not reasons to lower the threshold.

## Finite grid and conditional confirmation

Screen: encoded target64 MiB × steady/adversarial/bigrows × **seeds2703204357/2703204358** × baseline/candidate = six pairs / twelve native cells. Balanced arm order alternates by shape and repetition. Each job is one seed, three pairs/six cells, 840-second inner limit, wrapper wait850 seconds and outer900 seconds; child120 seconds. Build is a separate bounded job: two offline locked release example builds, `CARGO_BUILD_JOBS=2`, ≤360 seconds each. Frozen binary copies live in a fresh owned data-drive cache. Both builds clear all inherited `FABRIC_*_EXPERIMENT` variables then set run8 and the nominated ownership flag only; key-first remains unset. Source and protocol identities must stay frozen across both builds and all cells.

Only if all three shape screens pass in **both** screen seeds with every semantic gate true may confirmation run: same grid at **seeds2703204359/2703204360**, two more three-pair jobs. Driver admission authenticates the two completed screen summaries against the same frozen build-manifest hash. Confirmation does not refit thresholds. A cost-screen failure records a negative result while finishing the current finite seed job; semantic failure stops and preserves state. No additional seeds or context16 comparison are included.

Per pair require exact full regular-member path/length/SHA equality, covering the journal, every segment file and manifest, in addition to unchanged `memory_census.grade` logical ledgers/custody/metadata/no-leftovers. There are no intentionally differing fixture labels. Independent physical FTF1 reconstruction runs in the existing reaped PyArrow22 decoder subprocess and validates each file's own row groups. Logical rows are differential through existing Rust scanners, not an independent logical oracle. Native verification and content authentication precede successful cleanup. The harness rejects a representative mutated manifest content hash, as well as the existing missing/extra/content-change controls.

Metrics remain distinct: build requested live/incremental/retained heap and encoded throughput; whole-native CPU/wall/RSS; parent pre-spawn HWM; cgroup timeline; build process IO deltas; all disk bytes/maps. IO guard is a preregistered **±1% build write-byte ratio** around baseline, allowing only that finite measurement tolerance; exact member bytes remain unconditional. A zero baseline write counter is unknown and cannot establish this IO guard. No IO-gain claim is supported by this ownership-only mechanism. Reservation accounting and exclusive phase ownership remain unsupported.

## Containment, controls and commands

Evidence root is `docs/experiments/benchmarks/data/native-frontier-01/memory`; memory category cap512 MiB, with **192 MiB full-failure reserve** before every pair. Owned raw pair scratch≤512 MiB; aggregate scratch admission and data-drive free reserve follow the main protocol (8 GiB aggregate and16 GiB free). Passing states retain exact member maps/raw rows/checks/process receipts, not redundant fixture archives. On failure retain full compressed state within192 MiB, read back every path/size/SHA, then remove scratch; if preservation cannot complete, record exact partial archive and retain the original complete owned scratch. Decoder is a replaceable dependency with independent cleanup receipt. Binary cache remains tracked until root's final cleanup.

Before builds, root executes relevant bounded-sealer unit checks in baseline and candidate compile environments, including new lifetime controls (source ownership during write, converted-batch drop before flush, conversion failure retaining rows, write error in both policies, strict selector rejection), existing empty finalization, all-table byte/custody equivalence and corrupt-frame cleanup controls. These checks have **not run during preparation**. Builds, validators and native jobs run only through the root's serialized resource launcher; no uncapped fallback.
