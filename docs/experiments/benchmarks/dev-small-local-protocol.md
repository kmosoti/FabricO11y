# Sequential development and small deployment: local protocol

Registered before harness execution or workload measurements on `milestone/workload-sizing`, starting from `1740a60`. Native Linux processes only; no Docker, installation, privileged cgroup changes, faults, or qualification claim. Uses the [sizing model](../../research/workload-sizing.md), [Spindle collection](../../architecture/spindle.md), [durable delivery](../../architecture/delivery.md), and [retained storage](../../architecture/retained-history.md). The current branch includes the experimental streaming Parquet sink; the frozen source/binary hashes will be recorded. This is a two-workload observational pilot, not a writer comparison.

## Fixed workloads and sequence

Run development to completion, stop all its children, analyze/recover its state, then run small on fresh state. One trial per workload, seed 2703163393. No broad builds/checks or simultaneous experiments during either workload.

- Development: one real Spindle, aggregate 10 log events/s, 30/s during burst.
- Small: 20 real Spindles, aggregate 1,000 log events/s, 3,000/s during burst, equally divided.
- Each experiment: startup/enrollment and five-second settling, then 60 seconds ordinary load, 60 seconds 3× burst, 60 seconds ordinary recovery, followed by 20 seconds without new source lines for delivery/sealing to catch up. Then graceful node shutdown and graceful server shutdown, fresh-process durable replay, analysis.
- Deterministic 900-byte ASCII log bodies with unique node/tick/event tags; half repetitive and half seeded printable entropy. Each body is newline terminated. Metrics use the real collectors at 15-second intervals. No spans in this workload. **900 bytes is body size; the actual encoded bytes/event are measured rather than forced to the sizing model's 1 KiB.** File attributes, Batch/Group framing and native metrics add bytes.
- Producer uses monotonic 100 ms ticks, one event/node/tick in development, five/node/tick in small, tripled during burst. It catches up late ticks rather than silently dropping offers, and records lateness. Expected source logs are 3,000 and 300,000. Finite duration includes startup and recovery, not long retention/soak.
- Real durable Spool, TLS loopback, one Batch in flight per Strand, grouped two-sync commit, existing exact custody/projections, reclaim and retention are unchanged. Server `seal_workers=1`, `journal_file_bytes=64 MiB`, journal/retention byte ceilings 512 MiB, retention age 24 h; node Spool ceiling 256 MiB. The disk ceilings are trial overrides, not proposed production retention. Development is expected not to reach a seal at this rate; report that limitation rather than lowering its file threshold.

## Measurements and clocks

All endpoints share the same host. Two persisted data clocks are used per log: **collection** = OTLP `observed_time_unix_nano`, and **ingestion** = server `received_ns` recovered alongside exact Batch bytes from journal/Segments. Server received time is the commit group's timestamp before its syncs, not a timestamp proving durability. The independent Python query-oracle decoder reads the Batch/log clocks. Match by unique source tag, not positional sequence indexing.

Primary latency: `(received_ns - observed_ns) / 1e6` milliseconds, record-weighted p50/p99, overall and by source phase. Companion latency: collection to the harness's timestamp of the node's ACK stdout line. This includes durable commit plus return and stdout observation delay; it is not an exact native ACK timestamp. Also report native attempt `elapsed_us` p50/p99 and source flush to receive as an optional companion. Node collection timestamp is a cycle timestamp, not a separate per-record clock read. No source timestamp, server receive timestamp or ACK observation is substituted for another.

Use nearest-rank quantiles: sorted sample at `ceil(p*n)-1`; preserve sample counts/max/negative differences. Never clamp clock inversions. Sample `CLOCK_REALTIME - CLOCK_MONOTONIC` during the run to detect steps (range >5 ms flags clock uncertainty); same-host operation avoids cross-host offset but does not validate distributed clock synchronization. Records from one Batch share clocks and are correlated; one trial supplies no confidence interval.

Sample each second: server and individual/aggregate node RSS/high-water mark and CPU seconds from `/proc`, journal/Segment file sizes and sealed file count, Spool sizes and collected backlog from node stdout, child exit state. Report mean CPU equivalents (CPU seconds/wall seconds), peak RSS, acknowledged encoded Batch bytes, observed actual logs/s, disk/state volume and whether sealing occurred. These are process metrics, not a separately enforced 4 GiB host/cgroup limit. Affinity: two CPUs for server, two different CPUs for Spindles/producer; record actual allowed CPUs/quota. No claim that threads reserve those CPUs. Filesystem/cache/shared-host conditions are retained.

## Hypothesis/null and decision rules

For each workload, H1: this configuration keeps up with its offers, preserves all exact source logs and acknowledged bytes, completes cleanly, and has collection-to-ingestion p99 <=1 s, collection-to-ACK-observation p99 <=1 s, server RSS <=2 GiB and each node RSS <=64 MiB. H0: at least one criterion is not met. These are scoped pilot criteria, not contract/qualification changes. Production stability under long retention, queries, physical faults, and colder storage remains untested. Development's pre-seal result cannot establish its lifetime RAM requirement.

Correctness: replay all retained committed Batches after shutdown, independently decode every log, compare unique source identifiers and exact body SHA-256 against the producer record; reject missing/duplicate/changed/unexpected source logs, any collection gaps, any nonzero child exit, ACK whose native printed SHA-256 differs from recovered exact Batch bytes, or unrecovered ACK. Check contiguous recovered Strand sequence and no duplicate Batch keys. New comparison must reject a deliberate missing-record negative control before the workload trials. Preserve failures and all latency populations; no gate changes after seeing results.

## Bounds and evidence

Each experiment owned fresh scratch directory; refuse existing paths/symlinks. Per trial wall limit 900 seconds, logical trial disk limit 3 GiB, minimum workspace free space 4 GiB; monitor once/second, stop children and retain failure evidence on violation. Record resource sampling interval/possible overshoot. Server address-space limit 4 GiB; each node 512 MiB (address space differs from RSS). At most 64 MiB compressed retained evidence per trial after analysis; raw scratch custody/input files may remain inside the disk budget. SIGTERM/kill cleanup only for children owned by the runner. No unrelated data cleanup or host configuration changes.

Capture exact run command, source revision, harness/binary SHA-256, Rust release build settings, environment, generated source hashes/times, node ACK observations, recovered Batch hashes, per-record data clocks, resource samples, exit codes, gate verdicts and nulls. Trial artifacts go under `docs/experiments/benchmarks/data/dev-small-local-run-01/`; secrets/tokens/private keys stay in owned scratch and are never copied to repository evidence. A setup error corrected before the first trial is recorded separately without changing registered workload/criteria. Changes after a trial require a new registered revision.
