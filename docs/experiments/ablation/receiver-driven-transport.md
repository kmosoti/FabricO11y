# Receiver-driven transport research: Homa and SIRD

## Status and boundary

**Research plan with one network-limited H1 simulation cell executed; no Fabric O11y network transport exists.** Stage 5 ends at a local [durable commit](../../architecture/storage.md). This study asks whether receiver-driven scheduling can improve a future many-producer ingestion path without changing the [commit-before-ACK contract](../../architecture/delivery.md). A network GRANT or CREDIT authorizes transmission; it is **not** the durable acknowledgement that lets an upstream producer forget an event. The first [M0 versus M1 packet-slot result](receiver-credit-h1-run-01.md) addresses only the synthetic H1 hot-spot question and does not choose Homa or SIRD.

The [Homa SIGCOMM 2018 paper](https://people.csail.mit.edu/alizadeh/papers/homa-sigcomm18.pdf) combines an unscheduled message prefix, receiver-issued grants, receiver-chosen network priorities, and controlled overcommitment of active senders. The [SIRD NSDI 2025 paper](https://www.usenix.org/system/files/nsdi25-prasopoulos.pdf) uses receiver-issued credits while feeding sender-uplink and shared-network congestion signals back into credit allocation; its design does not require switch priority queues. These are research inputs, not selected Fabric O11y protocols. The papers use different implementations, networks, and workloads, so their published performance numbers cannot be compared as if they were one Fabric experiment.

The [Homa artifact](https://github.com/PlatformLab/homa-paper-artifact) and [SIRD simulator](https://github.com/epfl-dcsl/SIRD-Simulator) are possible references for later reproduction. The [Homa maintainers' simulator notes](https://homa-transport.atlassian.net/wiki/spaces/HOMA) warn that available simulators omit features relevant to incast. Before treating any external simulator as a full-protocol baseline, inspect its version, loss and timeout behavior, priority support, and incast handling. A Fabric mechanism study must be labeled **Homa-inspired** or **SIRD-inspired** unless it actually runs a validated implementation of the named protocol.

## Question and hypotheses

The application question is whether moving admission and transmission timing toward the receiver lowers tail latency and buffering when many producers send telemetry to one receiver. The separate network question is whether sender and shared-link feedback helps when several receivers compete for the same uplink or core link.

| Hypothesis to challenge | Expected observation | Counterevidence |
| --- | --- | --- |
| H1: receiver credits help incast | Lower p99 burst-peak receiver-plus-switch queued bytes at matched injection-interval goodput than a sender-paced baseline whose window does not know the active sender count | No improvement, reduced goodput, sender memory above its cap, or a burst that exceeds the receiver byte budget |
| H2: a Homa-inspired priority and active-grant package helps mixed sizes | Lower small-message p99 network completion without moving the cost to another size class or queue | Poor large-message completion, moved buffering, or no end-to-end gain at the later real-host gate |
| H3: SIRD-like sender and core feedback helps shared bottlenecks | Lower p99 core-link queue bytes at matched goodput with the same credit budget | No gain over receiver-only credits or feedback cost that erases the gain |

Fabric telemetry's eventual size and arrival distribution are unmeasured. The papers' RPC workloads also include many small messages, so their results cannot establish Fabric behavior by analogy alone. An unscheduled prefix can reduce small-message latency but can also synchronize into an incast burst. With `N` simultaneous senders each allowed `U` unscheduled bytes, up to `N × U` bytes can arrive before receiver credits constrain them. A fixed receive budget smaller than that amount cannot guarantee loss-free admission without another bound or an explicit overflow policy. This is a design constraint to test, not a measured Fabric result.

## Fair comparison and ablations

First keep **the same message trace, wire encoding, reliability/retry rule, sender and receiver queue byte caps, and ACK-after-commit rule** for every variant in a given regime. Change one scheduling mechanism at a time in a deterministic network model or controlled testbed. Receiver-credit variants need a first message announcement: with a zero-byte unscheduled prefix, the sender sends a metadata-only request so the receiver knows the message size and can issue credit. With a nonzero prefix, the first DATA packet carries that metadata. Count the request packet, its RTT, and all control bytes in the comparison; the SIRD paper describes a zero-length DATA request for messages scheduled from the start.

Use two named regimes. In the **network-limited** model the sink accepts complete messages immediately; only network completion and queue results can support a scheduling claim. In the **sink-limited** model every variant shares one receiver service-time trace calibrated from the Stage 6 log measurements; this is a latency model, not proof of actual durability. Set offered load against the smaller of network capacity and the measured sink capacity for that workload, and report both capacities. A later real-host run uses the same local log and measures actual durable-ACK completion; Stage 5's two syncs per event may dominate it. A local loopback run does not establish datacenter fabric behavior.

| Variant | Change from the named parent or control | Claim it can isolate |
| --- | --- | --- |
| M0: sender-paced baseline | Each sender has a fixed outstanding-byte window of one modeled bandwidth-delay product (BDP), independent of active sender count; no receiver scheduling | Reference cost and correctness for an uncoordinated sender window |
| M0-oracle: static equal share | Give each sender `C/N` of a known aggregate allowance `C` for `N` senders, including a one-packet minimum | Labeled knowledge-of-incast bound, not the H1 control |
| M1: receiver credits | Replace sender pacing with receiver-issued scheduled-byte credits; one active granted message, a global scheduled-credit budget of one BDP, no priorities or congestion feedback | Effect of receiver control and its aggregate credit cap, with total outstanding bytes reported |
| M2: unscheduled prefix | Add one packet of immediate data to M1; sweep `0` and one BDP only as sensitivity cases | Small-message latency versus incast buffer cost |
| M3: priority | Add four receiver-selected priority levels to M2; one queue is the M2 null control | Homa-inspired size scheduling contribution |
| M4: active-grant distribution | Use a calibrated active-grant degree from `{2, 4}` with M3 fixed; degree `1` is the M3 null control; hold aggregate granted-byte budget fixed within each comparison | Utilization versus queuing contribution of grant distribution |
| M5: matched-credit reference | From M2, use one priority class, fixed per-sender credit caps, and a global outstanding-credit budget `B` swept at `1`, `1.5`, and `2` modeled BDP; no congestion feedback | A matched reference for the SIRD-inspired feedback comparisons; M5 versus M2 does not isolate one cause |
| M6: sender feedback | Add sender-uplink congestion feedback to M5 at each **fixed** global `B` and fixed configured per-sender ceiling; feedback adapts the effective per-sender credit cap | SIRD-inspired response to busy senders |
| M7: shared-link feedback | Add ECN-like core feedback to M6 at the same global `B`, configured ceilings, topology, and workload; effective per-sender caps respond to both signals | Additional response to shared-link congestion |

M3/M4 and the matched M5→M6→M7 comparisons are **mechanism ablations**, not implementations or head-to-head performance claims about the complete Homa and SIRD protocols. Homa's active-grant degree and SIRD's global outstanding-credit budget `B` are distinct controls; label both explicitly in result tables. Holding M4's total granted bytes fixed isolates **distribution**, while Homa's overcommit also increases outstanding bytes; register a separate degree × granted-byte-budget sensitivity grid before making an overcommit claim. The SIRD paper's credit analysis motivates testing `B > BDP` when credits can be stranded at busy senders. M0 and M1 have the same physical sender and receiver queue caps but intentionally different aggregate network outstanding limits: this is part of receiver coordination, and queue occupancy, loss, latency, and the limits must be reported rather than attributed to priority. The M0-oracle bound shows what sender pacing could do with advance knowledge of `N`; it does not decide H1. Compare feedback off/on only at the same `B` and configured ceilings. If an actual protocol comparison becomes useful, run validated reference implementations under the same traffic and hardware in a separate record. Record whether switch priorities and ECN are available; do not silently emulate them in a real-host result.

For the labeled M0-oracle bound only, set `C = max(BDP, N × packet_size)` before evaluation, assign each of `N` known senders an equal `C/N` window (distribute any remainder in fixed producer order), and give its matched-credit reference a global `C` budget. This ensures every sender can send at least one packet. The oracle reference uses the same trace and physical byte caps but is analyzed separately from H1's M0 versus M1 comparison.

Choose one decision configuration for each tuned variant using calibration traces only: M3 priority cutoffs from a registered finite grid for the exact size mix, M4 active-grant degree from `{2, 4}`, and M6/M7 feedback thresholds from a registered finite grid. M2's one-packet prefix and M3's four queues are fixed before calibration and inherited by both branches; the null controls and other prefix values are sensitivity cases. For M5–M7, fix the configured per-sender credit ceiling at `1 × BDP`; adaptive effective caps may fall below it. Select M3/M4 using H2's mixed-size small-message p99 cell; select M6 using H3's p99 sender-uplink queue cell and M7 using H3's p99 core-queue cell, both on the shared-bottleneck trace at `B = 1.5 × BDP`. At each parent-to-child step, choose the candidate with the lowest mean of its assigned metric over calibration seeds `100..104`, among candidates meeting the completion, goodput, byte-cap, and latency guardrails on those seeds; break ties by lower total queued byte-time, then by the listed candidate order. If no candidate qualifies, record that failure and do not choose an evaluation winner. Freeze the chosen settings and all grid values before evaluation; a separate prefix, queue, degree, or `B` sweep is sensitivity analysis, not a second chance to select a winner from evaluation seeds. M5–M7 are compared at the same predeclared `B` values, with `1.5 × BDP` as H3's decision point.

## Workloads to pin before execution

Use immutable, seeded message traces so every variant sees identical arrival times, destination, message bytes, and IDs. The current [generator](../../../src/generator.rs) provides only one small Gauge shape and reuses IDs across producer instances; a transport study must assign a stable `(producer, sequence)` identity and add a controlled size/batch trace without calling that shape representative production traffic.

The first synthetic matrix is:

| Case | Producers and receivers | Message shape | Stress |
| --- | --- | --- | --- |
| Small telemetry | 1 and 8 producers → 1 receiver | One serialized event per message | Low overhead and small-message latency |
| Mixed sizes | 8 producers → 1 receiver | Fixed seeded mix of small events, 4 KiB batches, and 256 KiB batches | Priority benefit and starvation |
| Incast | 32 producers → 1 receiver, synchronized bursts | Small events and 64 KiB batches in separate runs | Unscheduled burst and receiver budget |
| Shared bottleneck | 32 producers → 4 receivers across one modeled core link; each sender fans out to all four receivers in a fixed round-robin destination sequence | Same mixed-size trace with overlapping bursts from each sender | Sender/core feedback and fairness |

Run offered loads of 25%, 50%, and 80% of the regime's bottleneck capacity, plus a separately analyzed overload run. In the shared-bottleneck case, pre-register a core link whose capacity is below the aggregate sender and receiver link capacities, and burst timing that transiently overloads individual sender uplinks; report actual core and sender-uplink utilization and both feedback-signal counts. If one signal never occurs, H3 cannot support a claim about that feedback loop. Freeze link rates, propagation delays, packet size, buffer capacity, ECN threshold, exact message-size proportions, retry/loss model, overflow behavior, and a common drain deadline in the runnable experiment record **before the first comparison**. Use calibration seeds `100..104` only for the parameter selection described above, then evaluation seeds `0..9` for paired comparisons. Require at least 1,000 offered messages per reported size class per seed and 1,000 incast bursts per seed for a p99 target; record sample counts and uncertainty. The matrix is a proposed stress suite, not a claim about real observability traffic. A representative trace, if obtained later, is an additional workload rather than a silent replacement.

All variants use the same finite sender-queue and receive-admission byte caps. Packet loss follows one specified retransmission rule. On admission overflow, the receiver issues an explicit rejection without a durable ACK; the sender retains the event and uses the same retry/backoff rule in every variant. The normal-load advancement gate below allows no such rejections. The overload run reports them and never supplies a normal-load latency winner. Count bytes waiting at senders as queued bytes, including messages held for credits or a sender window.

## Measurements and decision rule

Capture separately the trace release/application enqueue time, first wire-send time, complete receiver arrival time, durable-commit time, and sender receipt of the durable ACK. Define **network completion latency** as complete receiver arrival minus trace release, so time waiting in the sender queue is included. Report first-send-to-arrival time separately to expose transport service time. Define **durable-ACK latency** as sender receipt of the post-commit ACK minus trace release. Measure **achieved goodput** as bytes completed by the end of the fixed injection interval divided by that interval's duration, excluding the later drain; offered goodput uses all bytes released during the same interval. Report both rates and use achieved goodput for the 5% match gate. Report p50 and p99 for both latencies by size class and workload; achieved goodput versus offered load; peak and time-weighted p99 sender, receiver, and switch queue bytes; packet loss/retransmission; credits and control bytes per data byte; producer fairness; CPU and allocations for real Rust runs. For incast, take the maximum simultaneous **receiver plus switch** queued bytes during each burst, then report p99 across bursts. This is H1's targeted hot-spot metric. Also report total sender-plus-receiver-plus-switch queued byte-time and peak bytes: receiver credits may deliberately move waiting to bounded sender queues, and a reduced hot-spot peak is not a claim of reduced system-wide memory. Count all offered messages: report completed, rejected, timed out, and still pending at the common deadline. Never compute a favorable p99 by silently filtering failures; treat them as infinite latency in an offered-message distribution and report completed-message latency separately.

The correctness gate precedes ranking: no durable ACK before commit, no acknowledged event missing after the modeled receiver crash, no silent loss, finite byte bounds or observable rejection, and no duplicate durable record for the same stable `(producer, sequence)` when a lost ACK causes a retry. Credit and admission alone do not transfer ownership: the sender retains a retryable copy until the post-commit ACK. The current log and generator do not yet provide this network identity or deduplication rule. In the normal 25–80% load cases, **every offered message must complete by the common deadline with no application rejection** for a variant to advance; the overload case is diagnostic and ranked separately.

Name one primary target per hypothesis before running: **H1:** M1 versus M0 with their stated outstanding limits and the same physical byte caps, 64 KiB-batch 32-to-1 incast at 80% offered load, using p99 burst-peak receiver-plus-switch queued bytes; small-event incast and the M0-oracle bound are separate sensitivity cases. **H2:** M4 versus M2 on the 8-to-1 mixed-size trace at 80% network load, using the small-message p99 network completion latency; report M3 versus M2 and M4 versus M3 to attribute the parts. A claim that **both** priority and active grants helped also requires each incremental comparison to improve small-message p99 under the same guardrails. **H3:** M7 versus M5 at `B = 1.5 × BDP` on the 32-to-4 shared-bottleneck trace at 80% network load, using p99 core-link queue bytes; report M6 as the sender-feedback intermediate and repeat at the other registered `B` values as sensitivity checks. A claim about both feedback loops requires both signals to occur, M6 to improve p99 sender-uplink queue bytes versus M5, and M7 to improve p99 core-link queue bytes versus M6, under the same guardrails. These target cells are network-limited simulation results. The sink-limited model and later real-host result separately show whether any gain reaches durable ACKs.

A target passes the preliminary advancement rule only when the mean paired per-seed reduction in its named primary metric is at least 10% and a 95% paired-bootstrap interval for that mean has a lower improvement bound above zero. If a control seed has zero target queue occupancy, the relative reduction is undefined and the target is inconclusive; report absolute queue bytes instead. Compare at the same offered trace. For **every calibration and evaluation seed used in a primary comparison**, each variant must complete at least 95% of offered bytes by the end of the injection interval; otherwise the target is inconclusive at that load, even if all messages finish during the later drain. Call goodput **matched** only when injection-interval achieved goodput differs by at most 5%; otherwise the target fails this gate and the throughput-latency frontier is descriptive only, without extrapolation. Guardrails require every size class's and every active producer's p99 network completion no more than 5% above its matched control, and maximum per-class completion latency no more than twice the control's maximum. H2 also requires each queue location's p99 bytes no more than 5% above control (or one packet more if control is zero). H1 and H3 may move waiting to senders, so they require the common sender byte cap, the latency guardrails, and explicit reporting of sender queue occupancy and total queued byte-time; a lower receiver or core queue alone cannot be described as a system-wide memory improvement. Report per-producer goodput over the fixed injection interval as a separate fairness view; whole-run delivered/offered ratios would all equal one under the completion gate and would say nothing about scheduling fairness. Fixed byte caps and observed peaks remain separately reported. Final adoption requires a separate real-host end-to-end result, including durable-ACK latency and CPU cost; a network-only win does not select a protocol for Fabric O11y. No current evidence supports choosing Homa, SIRD, or either mechanism family.

## Correctness investigation and execution order

1. Measure the existing local generator, buffer, and log first, as [Stage 6](../../LEARNING_PATH.md#stage-6--measure-and-challenge-the-baseline) requires. Pin the message trace and its exact byte encoding, identities, batching, load generator, machine, and build settings.
2. Define a small transport state model before writing concurrent network code: credits issued/consumed once, scheduled bytes sent only with credit, finite receive admission, duplicate retry identity, retries after lost data or ACK, and ACK only after local commit. A TLA+ model can check the ordering and bounded state exploration; a budget inequality can be checked with Z3 if the allocation policy warrants it. State fairness assumptions separately from safety.
3. Validate the network model against analytic cases before ranking mechanisms: one-message serialization plus propagation time, conservation of sent and received bytes, and an `N × U` synchronized unscheduled burst. Inject an over-granting defect and require the credit checker to fail. Then implement the smallest runnable baseline and one mechanism at a time. Preserve exact commands, revisions, raw runs, counterexamples, and environment under `docs/experiments/`.
4. Validate simulation predictions on real hosts when the transport boundary exists. Separate end-host scheduling effects from switch priority and ECN effects, and do not extrapolate WSL loopback timings to a datacenter network.
